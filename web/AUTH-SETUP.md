# Авторизация Vera Privé

Реализован отдельный Node.js-сервер: Better Auth 1.7.25, SQLite, SMTP, email/пароль, Google, Яндекс и Telegram OIDC. Статический предпросмотр Sites не запускает этот сервер: формы показывают состояние подключения и не создают фиктивные аккаунты. Текущие ограничения доступа Sites сохранены.

## Локальный запуск и размещение

Нужен Node.js 24.15+ либо контейнер Docker и постоянный диск. Это конфигурация одного экземпляра приложения; для нескольких серверов потребуется общая база и адаптация конфигурации. На собственном домене сервер должен быть доступен по HTTPS через обратный прокси. Размещение: VPS Рег.ру, HTTPS через Caddy, домен shop.example.com.

1. `npm ci`.
2. Скопировать `.env.example` в `.env`, заполнить `APP_URL` точным origin домена (без завершающего пути).
3. Сгенерировать отдельный случайный `BETTER_AUTH_SECRET` (`openssl rand -base64 48`); хранить в секретах хостинга, не в Git и не в чате.
4. Настроить SMTP и адрес `MAIL_FROM`. Без них email-регистрация и восстановление отключены. Подтвердить адрес/домен отправителя у почтового провайдера.
5. `npm run db:migrate`, затем `npm start`.
6. Для Docker смонтировать постоянный том в `/app/data`, передать переменные окружения. Не выставлять Node-порт напрямую в интернет: перед ним HTTPS-прокси. Указать в `TRUSTED_PROXY` только фактические IP/CIDR прокси и настроить перезапись X-Forwarded-For на входе. По умолчанию trust proxy выключен. Адрес для ограничителя запросов сервер подставляет сам, перезаписывая одноимённый клиентский заголовок.
7. Регулярно делать согласованные резервные копии SQLite вместе с журналом WAL либо через SQLite backup API. Не копировать только открытый основной файл БД.

Нельзя потерять том `data` при перезапуске контейнера. Секрет, БД, SMTP-пароль и OAuth-секреты не входят в статический архив Sites.

## Социальные входы

У каждого провайдера нужны CLIENT_ID / CLIENT_SECRET и точный callback:

| Провайдер | Callback после APP_URL |
| --- | --- |
| Google | `/api/auth/callback/google` |
| Яндекс | `/api/auth/callback/yandex` |
| Telegram | `/api/auth/callback/telegram` |

Google: создать OAuth web client, добавить redirect URI. Яндекс: приложение Яндекс ID с правами login:email и login:info. Telegram: в BotFather открыть vera_prive_bot → Login Widget, добавить origin и callback, получить OIDC Client ID/Secret (это отдельные настройки, не нужно вставлять Bot API token в сайт).

Telegram не передаёт email: внутри БД используется служебный идентификатор на домене `.invalid`, который не отображается как контакт и не получает письма. Автоматическое объединение аккаунтов по email отключено; при совпадении email с существующим аккаунтом вход может потребовать прежний метод авторизации. Google можно подключить к существующему аккаунту кнопкой «Подключить Google» после входа: подтверждённая почта должна совпадать, сессия — не старше 10 минут. Автоматическое объединение по-прежнему запрещено.

Кнопки доступны только при наличии конфигурации. После успешного возврата от Google статус подключения берётся из серверной таблицы account. Реальные OAuth-переходы и доставку писем нужно проверить после подключения ключей и домена; тестовые ключи не имитируют успешный социальный вход.

## Права и границы готовности

Регистрация создаёт только customer. Роль и supplierId нельзя задать через публичную форму. После регистрации и подтверждения почты администратор сервера назначает роль командой:

```
node --env-file=.env server/set-role.mjs owner@example.com admin
node --env-file=.env server/set-role.mjs partner@example.com supplier s1
```

Изменение роли отзывает активные сессии. Endpoint `/api/access/:role` проверяет роль на сервере; профиль `/api/me` требует действующей сессии. Пароли хеширует Better Auth, cookie HttpOnly, production Secure, проверка Origin включена, восстановление отзывает старые сессии, вход ограничен по частоте.

Сервер хранит аккаунты, подтверждения и сессии. Каталог, заказы, адреса, выплаты и скидки **пока остаются демонстрационными данными браузера**, отделёнными по ID аккаунта. Это не серверная система торговли. Личные сведения из демонстрационного профиля автоматически на сервер не переносятся. Разделение ролей не заменяет будущую серверную проверку каждой операции с товарами и заказами.

## Проверки

`npm test`: регистрация, отклонение подмены роли, подтверждение email, неверный пароль, вход/выход, восстановление, одноразовость токена, отзыв сессий, конфигурация, существующие проверки магазина. Тестовые письма перехватываются в памяти; реальные письма не отправляются.

## Подтверждение email кодом

Пароль — от 8 до 128 символов, с повторным вводом. После регистрации клиент вызывает `/api/auth/email-otp/send-verification-otp` с `type: email-verification` и показывает отдельный экран ввода кода. Код состоит из 6 цифр, действует 300 секунд, хранится в виде хеша и используется один раз. После 5 неверных попыток нужен новый код. `/api/auth/email-otp/verify-email` подтверждает почту и создаёт защищённую сессию.

Повторная отправка ограничена 60 секундами на email в SQLite, независимо от IP и перезагрузки страницы. Отклонённая повторная отправка не изменяет активный код. Принятая отправка заменяет старый код. Неподтверждённый пользователь может войти с паролем и перейти к запросу кода. Восстановление пароля остаётся по одноразовой ссылке; оба вида писем имеют HTML и текстовую версию. Пароли и коды не сохраняются в sessionStorage, там только email и время следующего запроса.

Обновление VPS с Mac: `bash /path/to/project/web/deploy/upload-from-mac.sh`. Скрипт сохраняет существующий `.env` и том базы аккаунтов.

Повторные запросы восстановления пароля в течение 60 секунд возвращают тот же успешный результат без отправки новых писем и создания токенов. Защита действует по email на сервере, включая одновременные запросы. На форме показан отсчёт. Пошаговая настройка OAuth: `deploy/OAUTH-SETUP.md`.

Профиль: Яндекс first_name (или login, если имя отсутствует) и sex (male/female/пусто); gender хранится в user, миграция выполняется при запуске контейнера. Пол необязателен и редактируется. Смена email через /email-otp/request-email-change и /email-otp/change-email требует активной сессии, код привязан к пользователю и новому адресу, срок 300 секунд, повторная отправка через 60 секунд. Старый адрес остаётся до подтверждения. Дата рождения хранится на сервере и редактируется в профиле.

Яндекс запрашивает login:birthday вместе с login:info/login:email. Полная дата рождения проверяется на существование и отсутствие будущей даты; неполные даты Яндекса (нулевой год/месяц/день) не подменяются вымышленными значениями, пользователь может заполнить дату в профиле. Скидка ко дню рождения пока не реализована: размер и условия будут заданы отдельно.

Телефон удалён: не запрашивается у Яндекса, не сохраняется в профиле/API. При запуске новая версия удаляет прежнюю колонку phone, при открытии сайта очищает поле в локальных профилях браузера. Резервные копии хостинга отдельно не изменяются.

## Текущее поведение социальных входов

Входы Google и Яндекс автоматически присоединяются к существующему пользователю по совпадающему email, только если локальная почта уже подтверждена. Для Google используется emailVerified провайдера, для Яндекса доверяем default_email из его авторизованного API (у ответа нет отдельного флага email_verified). Яндекс включён в trustedProviders. Новые аккаунты Яндекса с неподтверждённой локально почтой перед объединением с другим способом должны подтвердить её кодом. ID, роль и данные существующего аккаунта сохраняются. Разные email не объединяются. Ручная привязка отключена, кнопки подключения удалены.

Telegram как способ входа полностью отключён, даже при наличии старых ключей в окружении. Ссылки на канал и бота в контактах сохранены. Старые аккаунты/их данные не удаляются. Старые инструкции о подключении Telegram и ручной привязке Google выше больше не применяются.

## Серверные кабинеты и приглашения (15 ноября)

Вход един для всех: email / Google / Яндекс. После входа серверная роль направляет в кабинет покупателя, администратора или поставщика. Публичная регистрация создаёт только покупателя; роль из браузера не принимается.

После загрузки новой версии с Mac (`bash /path/to/project/web/deploy/upload-from-mac.sh`) владелец сначала регистрируется и подтверждает почту. Затем **на сервере**:

```sh
bash /opt/vera-prive/deploy/make-admin.sh
```

Скрипт запросит email и назначит роль существующему подтверждённому аккаунту. Сессии будут отозваны; нужно войти заново. Пароль и OAuth-ключи не менять. Для администратора пока нет второго фактора: отдельный завершённый сценарий 2FA и восстановления требуется до расширения доступа сотрудников.

Поставщик: «Администратор → Поставщики → + Поставщик», открыть созданную карточку → «Приглашения и доступ», указать почту. Ссылка действует 7 дней, хранится в базе только в виде SHA-256, принимается один раз и только аккаунтом с совпадающей подтверждённой почтой. Неиспользованное приглашение можно отозвать. После принятия пользователь повторно входит и получает свой кабинет. Отзыв приглашения не отзывает уже выданную роль; для снятия существующего доступа оператор сервера использует `node server/set-role.mjs email customer` внутри контейнера (сессии отзываются).

Товары, поставщики, заказы, выплаты, чеки, корзины, избранное и адреса теперь хранятся в SQLite в существующем Docker volume `accounts`. Все изменения проходят серверную проверку и транзакцию; прямой перезаписи состояния клиентом нет. Поставщик видит только свои товары, строки продаж и выплаты; цена и публикация принадлежат администратору. Комиссия 15%, начисление 85% после ручного подтверждения продажи. Заказ фиксирует цену на момент заявки, онлайн-оплата и доставка не подключены.

Рабочая база начинается с пустого каталога и учёта. Старые демонстрационные товары, продажи и выплаты из localStorage не импортируются. Статический предпросмотр остаётся демонстрационным. Фото и чеки на этом этапе хранятся в JSON SQLite (фото до 8 шт., чек до 2 МБ); для большого каталога следует вынести файлы в объектное хранилище. Резервные копии должны включать `accounts` volume, а не только исходники.

### Удаление поставщика и архив

При создании поставщика теперь обязательны имя/название и email; email сразу подставляется в приглашение. В карточке поставщика появилась кнопка «Удалить поставщика» с подтверждением последствий. Сервер помечает поставщика удалённым, архивирует все его товары, отзывает неиспользованные приглашения и сессии привязанных аккаунтов, снимает роль поставщика. Аккаунты покупателей не удаляются. Архивные вещи нельзя заказать из старой корзины или подтвердить в ожидающей заявке; заявку можно отменить. История продаж, чеки и остаток долга сохраняются, остаток можно выплатить через карточку удалённого поставщика. Архив доступен администратору через пункт «Архив»; в публичный API товары архива не попадают.

### Позиционирование и состояние товара
На главной указаны Resale Shop и «100% оригинал», размещена ссылка «Новое с биркой» (`#/new-with-tags`). В форме товара доступен флаг `newWithTags`, сохраняемый сервером; по умолчанию старые товары не считаются новыми с биркой. Подборка сочетает этот признак с категорией, ценой, брендом и размером, исключая неопубликованные и архивные вещи. В карточке и при оформлении размещено: «Обмен не предусмотрен. Возврат — в случаях и порядке, предусмотренных законом». Это краткое уведомление, не полная политика возврата; обязательные права покупателя не исключаются.

### Каталог: состояние, поиск и ссылки
Главная и каталог используют один поиск по бренду/названию. Первый уровень каталога: все вещи, новое с биркой, б/у; состояние сохраняется при переходе между категориями. В текущей двухгрупповой модели товары без отметки `newWithTags` относятся к б/у. Новые отмечаются светлой меткой на фото. На главной — горизонтальная лента до 12 доступных поступлений. Фильтры раскрываются слева на desktop, список брендов прокручивается отдельно. Повторное меню в подвале убрано; WhatsApp остаётся неактивным до добавления ссылки.
